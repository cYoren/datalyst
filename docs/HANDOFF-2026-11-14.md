### Which database this is — read before touching anything

Datalyst's database is **its own Supabase project**. It is not shared with any other product.

| | |
| --- | --- |
| Supabase project ref | `ccgprpgwntuaealojtch` |
| Database host | `db.ccgprpgwntuaealojtch.supabase.co` |
| Auth for the app | the same project (`NEXT_PUBLIC_SUPABASE_URL` in `~/.config/cf-sites/datalyst.env`) |
| Cloudflare binding | `HYPERDRIVE`, id `b1d0c2ad9df9467abb2268bc5cb25817`, declared in `wrangler.jsonc` |

Three things that are easy to get wrong:

1. **Do not confuse it with the two projects the Supabase CLI on this machine can see.**
   `supabase projects list` returns `kcpucflegiydxhktathb` ("Medhub") and `blcklsldgzdgceyksbnm`
   ("Misc"). Neither is Datalyst. The `~/.supabase/access-token` here belongs to an account that
   cannot reach `ccgprpgwntuaealojtch` at all, which is why this step did not happen automatically.
   Running a migration against Medhub or Misc would be a production incident on a different product.
2. **There is no "connector" to configure.** The only indirection between the Worker and the
   database is Cloudflare **Hyperdrive**, which is a connection pooler in front of that same Supabase
   Postgres — not an integration, not a second database. Hyperdrive's connection string is
   write-only through the API, so the password can only come from Supabase: project
   `ccgprpgwntuaealojtch` → **Settings → Database → Connection string**. If direct `:5432` is
   IPv6-only from the machine you are on, use the pooler host and port that page shows
   (`...pooler.supabase.com:6543`).
3. **Do not run `npx prisma migrate deploy` or `supabase db push`.** This repository's migrations are
   rendered into an offline, reviewed bundle (below) precisely because a blind `migrate deploy`
   would try to execute `0_postgres_baseline` against a database that already has that schema. The
   supported path is the bundle, in the order given.

### Why it mattered

The merge that landed this work also deployed it: Cloudflare deploys on merge, the database does
not. The deployed code selects five columns that do not exist yet. Until `apply.sql` runs:

  runs `SELECT 1`, and a missing column surfaces as **401**, not 500, because

### What to run

Run again only if the schema drifts; the recipe that was used, with `DATABASE_URL` unset because this
machine has no connection string, went through the Supabase Management API
(`POST /v1/projects/ccgprpgwntuaealojtch/database/query` with the project's personal access token):

```sh
export DATABASE_URL='postgresql://...'          # project ccgprpgwntuaealojtch only
cd ~/Documents/Coding/Datalyst-project

# 1. Render the bundle offline. No connection, no writes.
node scripts/prepare-db-rollout.mjs --out /tmp/datalyst-rollout
cat /tmp/datalyst-rollout/manifest.json          # record the three sha256s

# 2. Read-only. Both fail closed if the database is not at the pinned baseline.
psql "$DATABASE_URL" -f /tmp/datalyst-rollout/catalog-preflight.sql
psql "$DATABASE_URL" -f /tmp/datalyst-rollout/preflight.sql
# If either fails: STOP. The database is not at a baseline this repo can describe.
# Reconcile by hand (docs/MIGRATION_BASELINE.md) and do not improvise.

# 3. Apply, then prove the schema matches the code.
psql "$DATABASE_URL" -f /tmp/datalyst-rollout/apply.sql
psql "$DATABASE_URL" -f /tmp/datalyst-rollout/verify.sql
```

`apply.sql` is additive: 37 `ADD COLUMN IF NOT EXISTS` / `CREATE TABLE IF NOT EXISTS` /
`CREATE INDEX IF NOT EXISTS` statements and no drops. It is idempotent, so a second run is a no-op.

## 10. Rules that are not negotiable here

- **One worktree per task**, removed at the end. Never `/tmp` for a worktree (Turbopack refuses), and
  `node_modules` is a hardlink copy (`cp -al`), not a symlink.
- **Every change goes through a pull request**, never a push to `main`. The branch name carries the
  roadmap ID; the PR body carries the "Accept" line and whether it was met.
- **Never use a "pro" model** and never the local ollama model, anywhere, for anything.
  Delegated jobs go to `commandcode/deepseek/deepseek-v4.1-flash`, one at a time.
- **Review gate**: reviewed + green = merge. Codex is out of credits; an independent review has been
  done with pi/deeprelay. If you change code, review it (or delegate the review) before merging.
- **Never claim more than the code does.** The most common review finding in this repository is a
  comment, a doc line or a UI sentence that promises something the code does not do. If a thing is
  not done, the document says "not done" and why.
- **The database**: additive, idempotent migrations only; every new migration registered in
  `scripts/prepare-db-rollout.mjs` and, if server-owned, in `serverOnly` (the
  `scripts/check-migration-baseline.test.mjs` guard enforces both). Never a destructive statement.
  Never `prisma migrate deploy` against production.
- **Credentials** live in the Bitwarden ops vault, not on disk: `bwenv <item> -- <command>`,
  `restore.sh`, `verify.sh` in `~/.local/share/bitwarden-tools/`. Do not create `.env` files and do
  not grep for secrets.
- **Nothing goes to users without an explicit yes from Gus**: no OTA update, no store build, no
  submitted review, no price change, no paid listing.
- **`TMPDIR=~/.cache/tmp`** for vitest, tsc and builds on this machine, or the tmpfs fills and the run
  dies mysteriously.
